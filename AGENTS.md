# AGENTS.md — the contract for automated subagents

This file is binding for any agent (human or not) working in this repository. It exists so that
four agents can work at once, in isolation, without stepping on each other.

Read this before you touch anything. Then read `docs/detector-authoring.md` if you are adding a
detector, or `docs/subagent-playbook.md` if you are running a subagent loop.

---

## 1. Ownership map

Exactly one owner per file class. If a task needs a file you do not own, you file an issue; you do
not edit it.

| Path | Owner | Notes |
|---|---|---|
| `src/pcapforensics/models.py` | **core** | the schema. frozen after Phase 0 |
| `src/pcapforensics/index.py` | **core** | builds the only view detectors get |
| `src/pcapforensics/tshark.py` | **core** | the tshark boundary |
| `src/pcapforensics/data_ciphers.py` | **core** | crypto reasoning helpers |
| `src/pcapforensics/certificates.py` | **core** | openssl enrichment |
| `src/pcapforensics/data/*` | **core** | generated by `make regenerate` |

## 2. Isolation rules

1. **Stay inside your allowlist.** Your allowlist is written on your issue. Edits outside it are
   rejected in review even when they look like an improvement.
2. **One issue, one branch, one PR.** Branch name `agent/<issue-number>-<slug>`.
3. **Never import a sibling detector.** `detectors/a.py` must not import `detectors/b.py`. If you
   need shared logic, it goes into `index.py` (core-owned) via an issue.
4. **Never edit `models.py` to make your life easier.** Add the field in an issue with a proposed
   shape. Schema changes are a merge event, not a parallel event.
5. **No new runtime dependency** without an issue. Dev dependencies (pytest, scapy) are fine.
6. **Do not rebase or force-push** other agents' branches. If you need a core change, land the
   core issue first and rebase onto it.

## 3. What "done" means

A task is done when **all** of these are true. Review checks them mechanically.

- [ ] The detector lives in its own file, is named `dN.<slug>`, and has `enabled = True` only if
      it produces findings on at least one fixture.
- [ ] `detect()` is a pure function of the `CaptureIndex`: no file I/O, no network, no globals.
- [ ] Every finding has a **stable** `code` (SCREAMING_SNAKE) and a `scope` that is unique per
      flow/host so `Finding.id` is stable across runs.
- [ ] Every finding carries at least one `Evidence` with a real frame number and a non-empty value.
- [ ] Every finding carries `remediation` and at least one `references` entry when a standard
      applies. A finding a reader cannot act on is not finished.
- [ ] Unknown or unparseable input produces a **finding or a note**, never a silent pass.
- [ ] No secret material can reach a report. If you touch credentials, use
      `index.redact_auth` or add a redaction of the same shape, and add a test.
- [ ] A synthetic fixture exists under `tests/fixtures/`, is generated by
      `scripts/make_fixtures.py`, and is deterministic.
- [ ] Tests assert on **finding codes**, not on prose.
- [ ] The detector row in the README table is updated.
- [ ] `make verify` is green: `ruff check .`, `mypy` (strict), `pytest`.
- [ ] `pf doctor` still passes.

## 4. Honesty rules

These are the project's rules about itself, and a reviewer will fail a PR that breaks them.

- Do not claim a fact the capture does not contain. If forward secrecy is undecidable, the answer
  is `None` with a reason, not `False`.
- Do not round a heuristic into a certainty. If it is a heuristic, set `confidence="low"`.
- Do not use a severity to express urgency rather than impact.
- Do not suppress a finding because it is noisy. If it is noisy, that is a policy conversation,
  and the policy lives in `docs/severity-model.md`.
- If you find a bug in core while working, **do not fix it in your PR**. File it, link it, and keep
  your detector working against the current contract.

## 5. Severity and confidence

Severity answers "how bad is this if true"; confidence answers "how sure am I from this capture".
They are independent and both are required.

| Severity | Use when |
|---|---|
| `critical` | credential or key material is exposed, or a prohibited cipher is negotiated |
| `high` | confidentiality of captured traffic is at risk without user action (no PFS, deprecated version, cleartext media) |
| `medium` | downgrade surface, policy violations, likely-relevant heuristics |
| `low` | legacy fields, weak hints, context a reviewer should see |
| `info` | inventory and clustering that is not a defect on its own |

`confidence` is `high` only when the evidence is directly visible in the capture.

## 6. Communication

- Issue title: `detector: <what it detects>` or `core: <what changes>`.
- Issue body must name the affected paths, the input that reproduces it, and the expected output.
- PR description: what you saw, what you changed, what you verified, and what you deliberately did
  not do.
- If you could not finish, say so in the PR. A partial detector behind `enabled = False` is a
  useful contribution; a half-working enabled detector is not.
